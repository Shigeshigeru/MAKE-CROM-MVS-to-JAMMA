SVC用の暗号化プログラム svcenc.c を作りました。この環境にはWindows用のコンパイラがないため、exeにはしていません。お手元でビルドしてください。

MAMEのソース（neopcb.cpp と neocrypt.c）を取得して実装しました。MAMEのinit_svcpcbは、基板用の追加スクランブル（svcpcb_gfx_decrypt）を戻してから、CMC50の復号（cmc50_gfx_decrypt）を行います。このプログラムはその正確な逆順の変換です。

ビルド

Windows (MinGW): gcc -O2 -o svcenc.exe svcenc.c
Windows (Visual Studio): 開発者コマンドプロンプトで cl /O2 svcenc.c

使い方

svcenc selftest
svcenc enc c1 c2 c3 c4 c5 c6 c7 c8
svcenc enc region.bin
svcenc enc に渡す平文は、64MBの1ファイルか、8MB×8本（c1/c2、c3/c4…のバイト交互）です。
出力形式は -f で選びます。
word32（既定）: 16MB×4本（269-c1a.c1〜c4a.c4）。MAMEのsvcpcbaと同じ構成で、MS5と同系です。
linear: 32MB×2本（269-c1.c1、269-c2.c2）。MAMEのsvcpcbと同じ構成です。
raw: 64MB×1本です。
出力ファイルごとにCRC32を表示します。

検証したこと

9つのテーブルがすべて256値の置換になっていて、書き写しミスは見つかりませんでした。
乱数の64MBを暗号化し、MAME方式の復号で戻して完全一致しました（selftestが合格）。
8本入力と64MB1本入力で同じ出力になることも確認しました。

未確認の点

鍵 57: 暗号化に使う鍵（extra xor）です。MS5の19は確認できましたが、SVCの値は検索で取れず、記憶の値です。違っていてもプログラムは動きますが、ゲームが起動しません。-k で変更できます。
Sデータ（固定レイヤー）: 基板版ではC ROMの末尾0x80000バイトにS（固定レイヤー）が入っていて、MVS版とは追加の変換が違います。そのため平文の末尾にこの変換の逆を既定で掛けています。平文が既に基板用の形式なら -n を付けてください。
8本入力の並び: MVS版のc1〜c8が、16MBずつ4組のバイト交互という前提は記憶によるものです。64MB1本の方がこの前提に依存しません。
実機での動作: 実機での起動は試せていません。

検証のしかた
MAMEのsvcpcbaには、各チップのCRC32が公開されています（269-c1a.c1はe64d2b0c、c2aは249089c2、c3aはd32f2fab、c4aはbf77e878）。平文が正しく、鍵が合っていれば、word32の出力のCRC32と一致するはずです。ずれる場合は、鍵と -n の有無を切り替えて試してください。

MS5での使い方

svcenc enc -g ms5 c1 c2 c3 c4 c5 c6 c7 c8

-g ms5 を付けると、次のように切り替わります。

鍵が19になります（-k で上書きできます）。
Sデータの末尾変換の範囲が0x20000バイトになります。
出力名が268-c1.c1〜268-c4.c4（16MB×4本）になります。

MAMEのms5pcbの定義も確認しました。SVCと同じsvcpcb_gfx_decrypt、CMC50の復号、Sデータの処理の順で、違うのは鍵と固定レイヤーの大きさだけでした。MS5のCROMは16MB×4本のみなので、-f linear は使えません。

確認状況

自己テスト（暗号化したデータをMAME方式で復号して戻す）は、MS5の設定でも合格しました。
実機やMAMEでの起動は試せていません。
MAMEのms5pcbのCROMはBAD_DUMPの扱いで、CRCが当てにならないため、SVCのようにCRCで照合することはできません。

IQさんのツールで作ったMS5のCROMが手元にあるなら、同じ平文からsvcencで作った結果とバイナリ比較してください。一致すれば、MS5でも確実に正しいと言えます。

なお、MS5のPROMやVROMの変換は別の作業になります。このツールはCROMだけの対応です。
